Web Security Research Laboratory
1. Общая идея проекта
Цель проекта — разработать веб-платформу для проведения контролируемых исследований безопасности веб-приложений и анализа их внешней поверхности атаки.
Платформа объединяет несколько специализированных инструментов информационной безопасности в единую среду, предоставляя пользователю удобный веб-интерфейс для запуска исследований, управления целями, хранения результатов, построения последовательностей проверок и формирования итоговых отчётов.
Проект ориентирован прежде всего на образовательные, исследовательские и лабораторные сценарии использования.
Основной принцип системы — не замена существующих средств информационной безопасности, а их интеграция в единую модульную платформу.
________________


2. Основные задачи
Платформа должна обеспечивать:
* регистрацию и аутентификацию пользователей;
* управление пользовательскими проектами;
* добавление и управление исследуемыми целями;
* запуск специализированных средств информационной безопасности;
* сбор и нормализацию результатов работы инструментов;
* хранение результатов исследований в централизованной базе данных;
* последовательное выполнение нескольких инструментов в рамках одного исследования;
* просмотр истории выполненных операций;
* отображение обнаруженных доменов, URL, endpoint'ов, технологий и других объектов;
* формирование структурированных результатов исследования;
* экспорт результатов и создание отчётов.
________________


3. Архитектура системы
Платформа предполагает многоуровневую архитектуру.
Web Application Layer
Отвечает за:
* пользовательский интерфейс;
* регистрацию и авторизацию;
* управление проектами;
* управление целями;
* настройку исследований;
* просмотр результатов.
В качестве основной серверной технологии планируется использование PHP.
Data Layer
Центральное хранение информации осуществляется в реляционной базе данных.
Планируемые основные сущности:
* Users;
* Projects;
* Targets;
* Domains;
* IP Addresses;
* Services;
* Endpoints;
* Technologies;
* Parameters;
* Scans;
* Jobs;
* Findings;
* Evidence;
* Tool Runs;
* Reports.
Для реализации данного слоя планируется использование SQL и PostgreSQL.
Tool Execution Layer
Специализированные инструменты информационной безопасности запускаются как отдельные процессы или изолированные контейнеры.
Платформа передаёт инструменту нормализованный набор входных данных, получает результат его работы, обрабатывает его и сохраняет результат в централизованной базе данных.
Integration Layer
Для каждого подключаемого инструмента предполагается создание отдельного адаптера.
Адаптер отвечает за:
1. подготовку входных данных;
2. формирование параметров запуска;
3. выполнение инструмента;
4. получение результата;
5. преобразование результата в единый внутренний формат платформы.
Это позволяет подключать и заменять отдельные инструменты без изменения основной логики системы.
________________


4. Планируемая интеграция средств информационной безопасности
В рамках проекта планируется исследовать возможность интеграции специализированных инструментов различных категорий.
Reconnaissance
* Subfinder;
* Amass;
* Censys;
* Shodan;
* SecurityTrails.
HTTP и Web Analysis
* httpx;
* WhatWeb;
* Wappalyzer;
* LinkFinder;
* ParamSpider.
Content Discovery и Fuzzing
* Gobuster;
* ffuf.
Vulnerability Research
* Nuclei;
* дополнительные специализированные средства безопасности.
Набор инструментов не является фиксированным и может изменяться в процессе разработки в зависимости от результатов исследования их возможностей, совместимости и лицензирования.
________________


5. Унифицированная модель результатов
Различные инструменты возвращают результаты в различных форматах.
Поэтому одной из ключевых задач проекта является создание единого внутреннего формата данных.
Например, результаты различных инструментов должны преобразовываться в сущности:
* Target;
* Domain;
* IP;
* Service;
* Endpoint;
* Parameter;
* Technology;
* Finding;
* Evidence.
Это позволит объединять результаты нескольких исследований и строить взаимосвязи между ними.
________________


6. Система последовательного выполнения инструментов
Платформа должна поддерживать выполнение цепочек исследовательских операций.
Пример:
Subfinder
→ HTTPX
→ WhatWeb
→ LinkFinder
→ FFUF
Результат одного этапа может использоваться в качестве входных данных следующего этапа.
Данный механизм позволит автоматизировать повторяющиеся исследовательские процессы и сформировать единый workflow из нескольких независимых security-инструментов.
________________


7. Контейнеризация
Для изоляции отдельных средств информационной безопасности планируется использование Docker.
Каждый инструмент может рассматриваться как отдельный исполняемый компонент с собственной средой выполнения.
Предполагаемая структура:
Platform
→ Job Manager
→ Worker
→ Tool Container
→ Result Parser
→ Database
Контейнеризация также позволит фиксировать версии инструментов и уменьшить влияние различий в зависимостях между ними.
________________


8. Безопасность самой платформы
Так как сама система предназначена для исследований в области информационной безопасности, отдельное внимание должно уделяться безопасности инфраструктуры платформы.
Планируется реализовать:
* аутентификацию и авторизацию;
* разграничение доступа пользователей;
* журналирование действий;
* контроль запуска инструментов;
* изоляцию процессов;
* ограничение ресурсов;
* хранение истории операций;
* возможность работы с лабораторными и заранее разрешёнными целями.
________________


9. Исследовательский режим
Основное назначение платформы — проведение контролируемых исследований.
Для разработки и демонстрации предполагается использовать специально подготовленные лабораторные среды и приложения с известными уязвимостями.
Это позволит безопасно изучать различные классы веб-уязвимостей, тестировать интеграцию инструментов и сравнивать результаты различных методов анализа.
________________


10. Отчётность
Результаты исследований должны сохраняться в структурированном виде и быть доступны через веб-интерфейс.
В дальнейшем планируется добавить автоматическое формирование отчётов, содержащих:
* исследуемую цель;
* использованные инструменты;
* время проведения исследования;
* обнаруженные объекты;
* результаты проверок;
* подтверждающие данные;
* описание обнаруженных проблем;
* рекомендации по дальнейшему анализу.
________________


11. Перспективы дальнейшего развития
После реализации базовой платформы проект может быть расширен следующими направлениями:
* визуальный конструктор исследовательских workflow;
* распределённое выполнение задач;
* дополнительные security-инструменты;
* расширенная корреляция результатов;
* автоматическое построение attack-surface graph;
* интеграция систем threat intelligence;
* AI-assisted analysis и интеллектуальное планирование исследований.
AI-компонент рассматривается как перспективное направление развития и не является обязательной частью первоначального MVP.
________________


12. Технологический стек
Предварительный стек проекта:
* PHP — backend и серверная бизнес-логика;
* SQL / PostgreSQL — хранение данных;
* HTML / CSS / JavaScript — web-интерфейс;
* REST API — взаимодействие между компонентами;
* Docker — контейнеризация;
* Linux — серверная среда;
* Go / Python / Ruby — используемые сторонними security-инструментами компоненты;
* Git — управление исходным кодом и версиями.
Основная идея проекта заключается в использовании PHP и SQL для разработки собственной платформы, а специализированных инструментов — для выполнения отдельных задач исследования безопасности.
